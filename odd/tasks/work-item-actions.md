# Feature: work item actions
Objective: roadmap phase 6, first delivery. Comment on, change the state of, and reassign a work item from its detail, with the app staying read-only when the token cannot write.
Branch: feat/work-item-actions (carries the roadmap commit f9049e2) · Delivery: single-pr (forecast ~800 authored lines: Rust writes, then UI and docs; PR actions are the second delivery) · Test runner: `cargo test` (src-tauri), `pnpm exec tsc --noEmit`, `pnpm build`.

## Specs
- S1 Roadmap phase 6 (verbatim): "Work items: add a comment, change state, change the assignee." "Needs Read & Write scopes; the app must work read-only when the PAT lacks them (actions disabled with a hint)." "Every write runs in Rust, sends only validated fields, shows a confirmation for votes and state changes, and refreshes the item from the server afterwards (no optimistic writes)." "Split into two deliveries: work item actions, then PR actions." "Done when: each action round-trips against a test project and a read-only PAT hides the actions without errors."
- S2 (assumption) Write failures never sign out. Azure DevOps answers a token without the needed scope with 401 or 403 (not verified which), and `send` maps 401 to `Unauthorized`, which signs out. Writes use their own response mapping: 401, 203, redirect and 403 become one fixed-text "no write access" error that switches the open detail to its read-only hint; 400, 409 and 412 become a fixed "Azure DevOps rejected the change" error; no write error carries server text or the values sent.
- S3 (assumption) Read-only detection. A token cannot list its scopes. When a work item detail opens, Rust probes write access with a work item update that only validates (`validateOnly=true`, a single `test` of `/rev`), which saves nothing. Granted shows the actions; denied hides them behind a hint naming Work Items (Read & Write); any other probe outcome (or a detail without a revision) shows the actions, and a denied state or assignee write then switches that detail to the hint, while a denied comment write shows the denial inline and keeps the typed text (L12). An accepted write or probe is remembered for the session, so later details skip the probe; a denial is never remembered organization-wide, since a 403 may concern one item only (an area the user cannot edit). A new token (sign-in again) starts unknown.
- S4 (assumption) Validated fields. State: one of the states of the item's type (read from Azure DevOps by Rust before the write). Assignee: a member of the project's default team or the signed-in user, or unassigned. Comment: plain text, 1 to 4000 characters after trimming, control and format characters removed except line breaks, HTML-escaped by Rust. State and assignee updates carry a `test` of the revision the user saw, so a change made elsewhere is rejected instead of overwritten.
- S5 (assumption) UI. The detail gets a state picker and an assignee picker under the header and a comment box above the discussion. A state change asks for confirmation; comment and assignee do not (S1 names votes and state changes only). After every write, successful or not (L12), the item and its comments are read again from Azure DevOps; failures show inline next to the action, never as a banner that replaces the item.
- S7 Comment edit and delete (L7, L8): "debería de poder editar y eliminar comentarios, se puede?" then "en este mismo PR, dale". (assumption) Only the signed-in user's own comments (comment `createdBy.id` equals the session user id, as pull requests compare authors) offer actions. Edit is offered only when the stored text is plain: format not markdown, no tags other than `<br>` variants, only decodable entities, no leading or trailing whitespace (a save trims it); any other comment (formatting, mentions, markdown, including app comments in an organization that stores markdown) is delete-only, so an edit never drops formatting. Rust decides `isMine` and `editableText`; before a PATCH or DELETE it reads the single comment again and refuses unless it is the user's, not deleted, and at the version the user saw ("Reload the work item and try again"), since the update API has no revision test. Edited text goes through the same validation and escaping as a new comment. Delete asks for confirmation (amends S5) and Azure DevOps keeps it in History (`isDeleted`). After an edit or delete, successful or not, the comments are read again.
- S6 (assumption) Scope wording. Work Items (Read & Write) is optional, for work item actions. The `Forbidden` message, README, login placeholder and `CLAUDE.md` say so.
