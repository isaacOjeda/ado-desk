# Feature: pull request checks
Objective: roadmap phase 5. Show build and policy status on pull requests: a status dot in the list, and the builds and policies in the detail, linking to the run.
Branch: feat/pr-checks · Delivery: single-pr (forecast ~700 authored lines: Rust checks, then UI and docs) · Test runner: `cargo test` (src-tauri), `pnpm exec tsc --noEmit`, `pnpm build`.

## Specs
- S1 Roadmap phase 5 (verbatim): "PR list: one status dot (succeeded, failed, running, none). PR detail: builds and required policies with their state, linking to the run in Azure DevOps." "Adds the Build (Read) scope: update the `Forbidden` message in `error.rs`, the README and the login hint. Missing scope degrades to "status unavailable", never an error page." "Done when: a PR with a failed build shows it in the list and the detail, and a PAT without Build (Read) still loads everything else."
- S2 Data source (user decision, L2): "Policies + Build (Read)": policy evaluations (`_apis/policy/evaluations`, Code (Read)) plus the Build API (`_apis/build/builds`, Build (Read)) for every build of the PR, including non-policy CI runs.
- S3 (assumption) Detail data, all in Rust: one command reads the pull request (`pullRequests/{id}`: project id, full source ref, last merge source commit), its policy evaluations, and its builds: builds of `refs/pull/{id}/merge` plus builds of the source branch whose source version is the PR's last source commit, newest build per definition. Policies and builds fail independently: a failed half becomes "unavailable" data, never an error, a banner or a sign-out.
- S4 (assumption) List dot: a separate command, called after the list renders, for active pull requests only (at most 50, 4 requests at a time). The dot uses build-type checks only: build validation policies (`settings.buildDefinitionId`), status policies (`settings.statusName`), and `refs/pull/{id}/merge` builds when Build (Read) is available. Worst wins: failed, then running, then succeeded; none without build-type checks or when that pull request's checks could not be read. Reviewer, comment and work item policies only show in the detail.
- S5 (assumption) States. Policy: approved -> succeeded, rejected or broken -> failed, running -> running, queued -> queued, notApplicable -> hidden. Build: inProgress or cancelling -> running, notStarted or postponed -> queued, completed + succeeded -> succeeded, + partiallySucceeded -> partial, + failed -> failed, + canceled -> canceled. Dot: queued counts as running, partial as failed, canceled is ignored.
- S6 (assumption) Detail UI: a "Checks" section with the policies (required first, then optional) and the builds, each with its state and, for builds and build policies with a run, a link to the run built in Rust (`/{org}/{project}/_build/results?buildId={id}`). Unavailable halves say so: "Build status unavailable. The token may lack Build (Read)." Names are plain, bounded text.
- S7 (assumption) Scope wording: Build (Read) is optional (build status only). The `Forbidden` message, README, login placeholder and `CLAUDE.md` mention it as such.
