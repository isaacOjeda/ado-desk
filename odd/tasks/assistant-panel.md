# Feature: assistant-panel
Objective: a bottom panel that runs the user's own Claude Code in an embedded terminal, plus a local MCP server in Rust that lets Claude read what the user is viewing and, with confirmation, reply to comments. Roadmap phase 7.
Branch: feat/assistant-panel · Delivery: ask-on-risk, chain strategy feature-branch-chain (user's choice, 2026-11-12): child PRs target the tracker branch feat/assistant-panel, which goes to main in one final PR · Test runner: `cargo test` (src-tauri), `pnpm exec tsc --noEmit`, `pnpm build`.

## Specs
- S1 Assistant panel: "Me gustaría que se pudiera abrir un panel inferior con una sesión de cloud." / "Y por qué pon una terminal? Porque quiero que se use la suscripción que el usuario ya tiene." A bottom panel in the main window runs the user's installed, unmodified `claude` CLI in an embedded terminal (PTY in Rust, xterm.js in the webview). The app never reads, stores or passes Claude credentials; the user signs in through Claude Code's own flow. The binary is found through the user's login-shell PATH (a Finder-launched app does not inherit it) or a path set in Settings; when it is missing, the panel says so instead of failing.
- S2 Working folder: "la sesión de cloud habría que ver en qué carpeta se abre, lo que sea." (Assumption) The folder is set in Settings; by default an empty folder owned by the app in its data directory.
- S3 Context through MCP: "lo que me gustaría es que mi aplicación de Ado pueda pasar la información a cloud, no sé cómo, para que cloud pueda responder preguntas" / "lo importante es que yo pueda hacer algo con la información que estoy viendo en el momento y que pueda yo hablar con cloud para hacer preguntas" / "tal vez que se levante un MSP, no sé." ADO Desk runs a local MCP server (Streamable HTTP) that the panel's session loads through `--mcp-config`. Tools: `current_view` (what the main window shows: organization, project, work item or pull request), `get_work_item`, `get_pull_request` (description, reviewers, comment threads, changed files). Read tools serve the active organization only.
- S4 Ask about this (derived from S3): the work item and pull request details get an action that opens the panel and types a prompt about the item into the terminal, without pressing Enter, so the user can edit it.
- S5 Replies from Claude: "o incluso contestar comentarios, etc." MCP write tools: reply to a pull request thread, add a comment to a work item. Every write is confirmed in ADO Desk, showing the exact target and text, before it is sent; a write is never pre-allowed. Writes reuse the existing validation and `AzdoClient::write` (a denial never signs the user out). (Precondition) The phase 6 round trip against a test project has passed.
- S6 Security (derived, CLAUDE.md boundary): the server binds to 127.0.0.1 only, on a random port, and requires a per-launch bearer token, which reaches the session through an environment variable, never a file or the webview. It rejects requests whose Host is not the loopback address and port, or that carry an Origin header. Errors are fixed text and never echo input or server text. The PAT never leaves Rust.
- S7 Scope: "Andes que por ahora sea solo para cloud." Claude Code only; Codex is out of scope (the same MCP server could serve it later).
- S8 Naming (derived, https://code.claude.com/docs/en/legal-and-compliance): the feature is called "Assistant"; the Claude Code name is not used as a feature name, only in plain text ("runs Claude Code").
- S9 Docs: README, CLAUDE.md (new loopback server next to the "webview has no network" rule) and the roadmap phase 7 row.
